# Bybit Volume Spike Bot

Моніторить USDT-перпетуальні криптоф'ючерси на Bybit і шле алерти в Telegram при
різкому й статистично значущому зростанні об'єму торгів на 1-хвилинному таймфреймі —
з додатковим контекстом, який допомагає оцінити ймовірний напрям руху.

## Як це працює

**Відбір пар:**
- Бере топ-N криптопар за абсолютною зміною ціни за 24г через REST API Bybit
  (з фільтром за мінімальним оборотом, щоб відсіяти неліквідні пари).
- Автоматично виключає TradFi-контракти (акції, ETF, товари на кшталт NVDA, TSLA,
  QQQ, XAU) — моніторяться тільки криптовалютні пари.
- Кожні `REFRESH_INTERVAL_SEC` оновлює список топ-пар і перепідключає WebSocket,
  якщо склад пар змінився.

**Детекція сплеску:**
- Для кожної закритої 1хв-свічки рахує z-score поточного об'єму відносно середнього
  і стандартного відхилення за попередні N свічок (адаптується під волатильність
  кожної конкретної пари, на відміну від простого порогу "у X разів більше").
- Фільтрує за мінімальною зміною ціни (%), щоб не реагувати на сплески об'єму без
  реального руху ціни.

**Контекст напряму (додається до кожного алерту):**
- **Taker buy/sell ratio** — співвідношення купівель і продажів маркет-ордерами за
  останню хвилину (потік `publicTrade`).
- **Дисбаланс стакану** — співвідношення обсягу бідів/асків у топ-50 рівнях стакану
  (потік `orderbook.50`).
- **Open Interest** — росте (нові позиції, тренд імовірно продовжиться) чи падає
  (закриття позицій, можливий сквіз/розворот); опитується окремо раз на
  `OI_REFRESH_INTERVAL_SEC`.
- **Funding rate** — контекст щодо перекосу натовпу в лонги/шорти.
- **5хв тренд** — напрям останньої підтвердженої 5хв-свічки; порівнюється з напрямом
  сигналу ("за трендом" / "проти тренду — можливий розворот").
- **Патерн об'єму перед сплеском** — чи об'єм спадав, зростав чи був стабільним у
  останні кілька хвилин перед сплеском (ознака вичерпання руху).

При розриві WebSocket-з'єднання бот перепідключається автоматично.

## Локальний запуск (для тесту)

```bash
python -m venv venv
source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# заповнити TELEGRAM_BOT_TOKEN і TELEGRAM_CHAT_ID у .env

export $(cat .env | xargs)   # Linux/Mac; на Windows задати змінні вручну
python bot.py
```

## Як отримати Telegram-токен і chat_id

1. Написати @BotFather → `/newbot` → отримати `TELEGRAM_BOT_TOKEN`.
2. Написати своєму новому боту будь-яке повідомлення.
3. Відкрити в браузері `https://api.telegram.org/bot<TOKEN>/getUpdates` (весь токен
   одразу після `bot`, без пробілів) — знайти там `"chat":{"id":ЦИФРИ,...}`.

## Деплой на Fly.io (безкоштовний варіант)

```bash
# встановити flyctl: https://fly.io/docs/flyctl/install/
fly launch --no-deploy        # створить fly.toml, відповісти "ні" на автогенерацію
fly secrets set TELEGRAM_BOT_TOKEN=xxx TELEGRAM_CHAT_ID=xxx
fly deploy
```

Fly.io деплоїть безпосередньо з Dockerfile у цій папці — окремо нічого готувати не треба.

## Деплой на Oracle Cloud Free Tier VM (постійно безкоштовний варіант)

1. Створити безкоштовну ARM-інстанцію (Always Free) в Oracle Cloud Console.
2. Підключитись по SSH, встановити Docker.
3. Скопіювати файли проєкту на сервер (`git clone` свого репозиторію).
4. Запустити:
   ```bash
   docker build -t volume-bot .
   docker run -d --restart unless-stopped \
     -e TELEGRAM_BOT_TOKEN=xxx -e TELEGRAM_CHAT_ID=xxx \
     --name volume-bot volume-bot
   ```

## Деплой через Railway (найпростіший git-flow)

1. Запушити ці файли у свій GitHub-репозиторій.
2. На railway.app → сервіс → Variables → додати `TELEGRAM_BOT_TOKEN` і
   `TELEGRAM_CHAT_ID` (саме у Variables сервіса, не в Shared Variables проєкту).
3. Railway сам збере образ за Dockerfile і задеплоїть; кожен наступний `git push` —
   автоматичний редеплой.

## Налаштування чутливості

Все керується змінними середовища (див. `.env.example`):

- `Z_SCORE_THRESHOLD` — на скільки стандартних відхилень об'єм має перевищити
  середнє, щоб спрацював алерт (за замовчуванням 3.0).
- `MIN_PRICE_CHANGE_PCT` — мінімальна абсолютна зміна ціни за свічку (%), нижче
  якої сплеск об'єму ігнорується (за замовчуванням 0.3%).
- `ROLLING_WINDOW` — скільки попередніх хвилин враховувати для середнього і
  стандартного відхилення (за замовчуванням 10).
- `MIN_VOLUME_USDT` — фільтр за мінімальним оборотом.
- `TOP_N_PAIRS` — скільки пар моніторити (за замовчуванням 25).
- `ALERT_COOLDOWN_SEC` — мінімальний інтервал між повторними алертами по одній парі.
- `REFRESH_INTERVAL_SEC` — як часто оновлювати список топ-пар (за замовчуванням
  1800 = 30 хв).
- `OI_REFRESH_INTERVAL_SEC` — як часто опитувати Open Interest по кожній парі
  (за замовчуванням 180 = 3 хв).

## Обмеження поточної версії

- Немає збереження стану між рестартами — історія об'ємів, стакану, taker-угод і OI
  накопичується заново при кожному деплої/рестарті.
- Фільтр TradFi-контрактів спирається на поле `symbolType` у відповіді Bybit
  instruments-info; якщо формат зміниться, фільтр мовчки перестане працювати
  (перевіряти кількість знайдених TradFi-символів у логах при старті).
- Кожна пара тепер підписана на 4 WS-топіки (kline.1, kline.5, publicTrade,
  orderbook.50) замість одного — це більше трафіку й навантаження на CPU/пам'ять,
  особливо якщо збільшувати `TOP_N_PAIRS`. На безкоштовних тарифах хостингу варто
  стежити за використанням ресурсів.
- Open Interest опитується через REST по одному символу за раз (Bybit не дає
  масового ендпоінту) — при великому `TOP_N_PAIRS` повний цикл оновлення OI по
  всіх парах займає довше, ніж `OI_REFRESH_INTERVAL_SEC`; це нормально, просто
  дані оновлюються з певним лагом.
- Дисбаланс стакану і taker buy/sell — миттєві метрики одного моменту/хвилини, не
  гарантія напряму, а додатковий контекст для власного рішення.
